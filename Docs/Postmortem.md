# 프로젝트 회고

## 1. 프로젝트 목표

RandomTowerDefence는 Unity 6 기반 2D 타워 디펜스 프로젝트다. 플레이어가 장애물을 설치해 타워 배치 기반을 만들고, 상점에서 구매한 타워 UID를 대기열에 보관한 뒤 유효한 장애물 셀 위에 타워를 배치하는 흐름을 구현했다.

주요 플레이 흐름은 다음과 같다.

- 장애물 설치
- 상점 구매와 대기열 보관
- 장애물 셀 위 타워 배치
- JSON 기반 웨이브 전투
- 전투 중 런 강화
- 계정 단위 메타 성장
- 로컬 JSON 옵션과 Firebase Firestore 진행 데이터의 분리 저장

기능을 하나의 클래스에 모으기보다 상태 소유자와 흐름 조정자를 나누고, 데이터와 이벤트를 통해 시스템을 연결하는 것을 목표로 했다.

## 2. 최종 결과

| 시스템 | 구현 결과 |
|---|---|
| Tower Build System | 구매한 타워는 즉시 필드에 생성되지 않고 UID가 대기열에 보관된다. 선택된 타워와 셀을 검증한 뒤 플레이어가 설치한 장애물 셀 위에 타워를 생성하고, 필드 등록 성공 후 점유 상태와 큐 상태를 갱신한다. |
| Shop & Queue System | 골드 사용 가능 여부와 대기열의 수용 결과를 확인한다. 빈 슬롯이 없으면 구매를 실패 처리하고, 구매 성공 시 타워 UID를 큐에 저장하며 실제 그리드 설치는 Tower Build System에 맡긴다. |
| Wave & Enemy System | JSON 웨이브와 적 로스터를 사전 검증하고 적 생성·이동·사망·도착을 관리한다. 스폰 상태와 생존 적 수를 함께 사용해 웨이브 완료를 판정한다. |
| Meta Upgrade System | 전투 중 적용되는 런 강화와 계정에 유지되는 메타 성장을 분리했다. 기본값과 각 강화 단계를 결합해 최종 스탯을 계산한다. |
| Save & Load System | 기기별 옵션은 로컬 JSON으로, 계정 진행은 Firebase Firestore로 분리했다. 원격 로드 결과와 저장 모델 유효성을 구분해 처리한다. |
| Quest & Achievement System | ScriptableObject 원본과 런타임 진행 객체를 분리하고 공통 보고 API, 완료 이벤트, 저장 데이터를 연결했다. |
| UI Info Panel System | Presenter가 표시 값을 만들고 View가 Unity UI를 조작하며 StageUIController가 입력과 게임 시스템을 연결한다. 패널 전환 중 중복 입력과 이벤트 생명주기를 관리한다. |
| Editor Tooling | Tower·Enemy·Item·Wave JSON 편집과 검증, Quest·Achievement 에셋 제작, Play Mode 디버깅을 Unity Editor 확장으로 보조한다. |

세부 구현은 [기술 문서 메인](README.md)과 각 Systems 문서에서 확인할 수 있다.

## 3. 잘된 점

- 상점 구매와 실제 타워 배치 시점을 분리하고, 구매한 타워 UID를 대기열이 보관하도록 구성했다.
- 대기열이 타워를 수용할 수 없으면 구매를 실패 처리해 골드와 큐 상태가 어긋나는 불완전한 상태를 방지했다.
- 타워 배치 시 장애물 존재 여부, 셀 유효성, 기존 타워 점유, 최대 설치 수, 필드 등록 결과를 단계적으로 확인했다.
- 설치 실패 시 큐를 유지하고 FieldTowerManager 등록 성공 후에만 설치 완료 이벤트로 큐를 제거했다.
- 타워, 적, 아이템, 웨이브, 강화 규칙을 JSON으로 관리해 밸런스와 콘텐츠 데이터를 런타임 로직에서 분리했다.
- C# 이벤트로 적 생명주기, 세션 상태, UI 입력, 퀘스트·업적 보고를 연결했다.
- 런 강화와 계정 단위 메타 성장을 별도 상태와 계산 단계로 관리했다.
- 로컬 JSON과 Firebase Firestore의 저장 대상을 분리하고 원격 로드 실패 상태를 구분했다.
- Unity Editor Tooling으로 데이터 제작, 참조 검증, 퀘스트 에셋 생성, Play Mode 테스트를 보조했다.
- 기능 구현 이후 README와 Docs에 클래스 책임, 이벤트·데이터 흐름, 문제 해결 과정과 현재 한계를 정리했다.

## 4. 어려웠던 점

구매 자체보다, 큐에 보관된 타워를 실제 필드에 배치하는 과정의 검증 조건을 일관된 순서로 처리하는 작업이 더 까다로웠다.

- 선택한 큐 슬롯에 유효한 타워 UID가 있는지 확인해야 했다.
- 선택한 셀이 그리드 범위와 설치 규칙을 만족하는지 확인해야 했다.
- 플레이어가 설치한 장애물이 존재하고 기존 타워가 점유하지 않은 셀인지 확인해야 했다.
- 타워 생성 이후 FieldTowerManager 등록까지 성공해야 설치 완료로 처리할 수 있었다.
- 설치 실패 시 큐 상태를 유지하고, 설치 성공 시에만 큐를 제거해야 했다.
- 웨이브에서는 스폰 종료와 생존 적 0명 조건이 서로 다른 시점에 발생하므로 두 상태를 함께 검사해야 했다.
- 스테이지 런 상태와 계정 영구 성장 데이터의 수명주기와 저장 경계를 분리해야 했다.
- DOTween과 Animator를 사용하는 UI 패널 전환에서 입력과 완료 콜백이 겹치지 않도록 관리해야 했다.
- Firestore 문서 없음, 권한, 네트워크, 시간 초과, 데이터 손상을 서로 다른 결과로 처리해야 했다.
- 반복적인 JSON 편집과 참조 검증을 수작업에만 의존하지 않도록 Editor Tooling을 구성해야 했다.

## 5. 주요 문제 해결 사례

### 5-1. 큐 기반 구매와 타워 배치 검증 분리

- **문제:** 구매한 타워는 즉시 필드에 생성되지 않고 큐에 보관되며, 이후 선택한 장애물 셀에 배치해야 했다. 구매 이후의 실제 배치 검증 조건이 여러 상태에 걸쳐 있었다.
- **해결:** 상점은 골드와 대기열 수용 결과를 처리하고, Tower Build System은 큐 선택, 셀, 장애물, 점유, 생성, 필드 등록을 검증하도록 책임을 나눴다.
- **결과:** 큐가 타워를 수용하지 못하면 구매를 실패 처리하고, 설치 실패 시 큐를 유지하며, 필드 등록 성공 시에만 큐를 제거한다.

자세한 흐름은 [Case Study](Portfolio/CaseStudy.md#사례-1-타워-구매와-건설-흐름-분리)에서 확인할 수 있다.

### 5-2. 장애물 기반 타워 설치 조건 검증

- **문제:** 타워는 임의의 그리드 셀이 아니라 플레이어가 설치한 장애물 셀 위에만 배치되어야 했다.
- **해결:** 선택 셀의 범위와 시작·도착점 여부, 장애물 존재, 기존 타워 점유, 최대 타워 수, 필드 등록 가능 여부를 순서대로 검사했다.
- **결과:** 유효한 배치 조건과 필드 등록이 모두 성공한 경우에만 설치를 완료하도록 경계를 명확히 했다.

세부 검증 단계는 [BuildSystem](Systems/BuildSystem.md)에서 확인할 수 있다.

### 5-3. 웨이브 종료 조건 처리

- **문제:** 적 스폰 종료와 생존 적 수가 0이 되는 시점이 서로 달랐다.
- **해결:** isSpawning과 aliveEnemyCnt를 별도로 관리하고 스폰 종료, 적 사망, 적 도착 시 같은 완료 조건을 다시 검사했다.
- **결과:** 스폰이 끝나고 생존 적이 없는 경우에만 다음 웨이브 또는 스테이지 종료 흐름으로 이동한다.

자세한 이벤트 흐름은 [Case Study](Portfolio/CaseStudy.md#사례-2-웨이브-종료-조건-처리)에서 확인할 수 있다.

### 5-4. 저장 실패와 데이터 검증

- **문제:** Firestore 문서 없음과 네트워크·권한·시간 초과·손상 데이터에 의한 로드 실패를 구분해야 했다.
- **해결:** Success, DocumentMissing, NetworkError, PermissionError, Timeout, DataCorrupted 등의 결과 상태와 IValidSaveData 검증을 적용했다.
- **결과:** 신규 사용자 기본 데이터 생성과 실제 로드 실패 대응을 별도 흐름으로 처리한다.

자세한 저장 경계는 [Case Study](Portfolio/CaseStudy.md#사례-3-저장-실패와-데이터-검증)에서 확인할 수 있다.

### 5-5. Editor Tooling을 통한 데이터 제작 보조

- **문제:** Tower, Enemy, Item, Wave JSON과 Quest 에셋을 직접 편집할 때 입력 오류와 참조 누락을 반복해서 확인해야 했다.
- **해결:** 데이터 테이블 EditorWindow, Validate 탭, Quest 제작 도구, Play Mode 디버거를 작성했다.
- **결과:** 데이터 편집, 검증, 테스트 입력을 Unity Editor 안에서 수행할 수 있는 제작 흐름을 구성했다.

실제 도구와 검증 범위는 [EditorTooling](Systems/EditorTooling.md)에서 확인할 수 있다.

## 6. 현재 한계

- 성능 병목 여부는 Unity Profiler 기반 측정이 필요하다.
- Enemy·Tower 생성과 파괴, 적별 경로 탐색, TowerAttack 타겟 탐색 비용은 실제 플레이 상황에서 추가 검증이 필요하다.
- 일부 조정 책임이 StageManager와 TowerController에 집중되어 있어 흐름별 조정 객체 분리를 검토할 수 있다.
- 저장 데이터의 schemaVersion과 버전별 마이그레이션 정책은 보완 여지가 있다.
- 그리드 검증, 큐 유지, 웨이브 완료, 저장 모델 검증 등 주요 규칙의 자동화 테스트를 보강할 수 있다.

## 7. 다시 개발한다면

1. StageFlow, BuildFlow, WaveFlow처럼 흐름별 조정 객체를 분리한다.
2. Tower Build System의 셀·장애물·점유·설치 수 검증을 독립적인 Validator 객체로 분리한다.
3. Unity Profiler로 생성·파괴와 경로 탐색 비용을 측정한 뒤 Object Pool 적용 여부를 결정한다.
4. TowerAttack 타겟 탐색 비용을 NonAlloc API 또는 적 공간 인덱스 구조와 비교한다.
5. 저장 데이터에 schemaVersion을 추가하고 버전별 마이그레이션과 실패 복구 정책을 정의한다.
6. 배치 가능 여부, 큐 유지, 웨이브 완료, 저장 데이터 유효성 같은 핵심 규칙의 자동화 테스트를 먼저 설계한다.
7. 데이터별 EditorWindow의 공통 저장·검색·검증 기능을 추출하고 통합 검증 도구로 정리한다.
8. Resources 문자열 경로 의존도를 줄일 수 있도록 설정 객체, Addressables 또는 별도 데이터 파이프라인을 비교한다.

## 8. 배운 점

- 구매 상태와 설치 상태를 분리하면 책임은 명확해지지만, 실제 설치 시점의 검증 순서와 실패 후 상태를 함께 설계해야 한다.
- 상태를 소유하는 객체와 여러 시스템의 흐름을 조정하는 객체를 구분하는 것이 변경 범위를 관리하는 데 중요하다.
- 이벤트 기반 구조는 직접 참조를 줄일 수 있지만 발행자, 구독자, 해제 시점을 문서로 함께 관리해야 한다.
- 데이터 기반 설계는 파일 분리뿐 아니라 UID, enum, 참조, 수치 범위를 확인하는 검증 도구가 함께 필요하다.
- 저장 시스템은 성공 흐름보다 문서 없음, 권한, 네트워크, 시간 초과, 손상 데이터 같은 실패 흐름의 구분이 중요하다.
- Unity Editor Tooling은 1인 개발에서 반복 입력과 테스트 절차를 줄이고 데이터 제작 안정성을 보조한다.
